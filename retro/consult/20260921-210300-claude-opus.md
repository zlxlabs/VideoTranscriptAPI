## 三、Q1：设计目标本身定错了吗？——是，但错在一个比你说的更具体的地方

你的论证是：「下游是 fire-and-forget 的 webhook，下游本身不可靠，所以应用层达不成 exactly-once。」

**这个论证方向对，但它是软的**——任何下游不可靠系统都能靠「at-least-once + 幂等」把用户体验做到位，不可靠本身不构成「别做机制」的理由。

**硬的版本是这个（事实 4/5/7/8）**：

```
outbox 标 sent  ←─ 持久化边界画在这里
      ↓
router 返回 {"wechat": True}   ← 常量 True，不是发送结果（wechat.py:239）
      ↓
manager.enqueue(message)        ← 进内存 queue.Queue（manager.py:55）
      ↓
daemon=True 工作线程            ← 进程退出即被杀，队列不排空（manager.py:64,86-107）
      ↓
真正的 HTTP POST
```

推论有三条，每条都可证伪：

1. **`sent` 是一句关于 daemon 线程的谎话。** 它证明的是「已入内存队列」，不是「已发出」。
2. **机制在它自己的设计点上失效。** 部署重启（SIGTERM → 解释器退出）会杀掉 daemon 线程、丢弃未发消息；而 outbox 此刻**已经标了 sent**，于是下次启动补发时**不会补它**。你为「重启不丢」建的机制，在重启时丢消息，且丢得比不建更隐蔽（因为 DB 里明明白白写着 sent）。
3. **`_notification_accepted` 的 fail-closed 判的是常量。** 企微/飞书 happy path 一律返回 `True`（事实 8/9），它只能在「webhook 未配置 / 内容为空 / 抛异常」时返回 False。第 2 轮那次加固，在主路径上**买到的东西接近于零**——它防的是「未知返回形态」，而返回形态是两个硬编码 `return True`。

**所以「恰好一次、必达」不是「难以达成」，是在当前投递实现下\*结构性地无法被观测\*，因而无法被断言、无法被测试、也无法被 review 收敛。** 每一轮 review 都在给一个观测不到的目标修防线——这正是不收敛的燃料。

### 但这不等于「别做 outbox」

outbox 唯一真正买到的东西，和持久化无关：**它把 13 个终态写入点、3 种通知语义收敛成 1 处**（事实 14/15 是这个问题今天仍然活着的证据，且它们活过了至少 R2/H2/K3/G1 四轮加固）。这个价值是真的，与 exactly-once 无关，你不该因为 §三的结论就把它一起扔掉。

### 把边界移到正确位置的办法（便宜，且是唯一让 attempts/重试有意义的改动）

投递线程本来就是后台线程，**它阻塞是它的职责**。所以：在 outbox 投递点改用 `async_send=False` + `SendResult.wait(timeout)` + `is_success()`（事实 12 已验证该 API 存在且有真实三态）。代价是要在 `wechat.py` / `channel.py` 旁开一个**不丢 result** 的发送入口（现有 `send_markdown_v2` 硬编码 `return True`，不能复用）。

改完之后：`sent` = 「HTTP POST 被接受」，`_notification_accepted` 判的是真实信号，重试有意义，「至少一次」第一次成为**可断言**的性质。**这一条的收益，大于 6 轮 review 加起来的收益。**

## 四、Q2：最小充分不变式 + 哪一条机制在单进程下根本不需要

### 裁决：选 (b) 的强化版，我叫它 (b+)。(a) 部分采纳，(c) 否掉。

### 4.1 不变式清单（可直接写成测试，逐条可证伪）

> **I1（终态 ⇒ 落账，原子）** 任一次 `update_task_status` 写入终态且 CAS 获胜，当且仅当同一事务内 `task_terminal_notifications` 出现该 task_id 的一行。CAS 落败 ⇒ 不出现任何行。
> **I2（唯一）** `task_terminal_notifications.task_id` UNIQUE。同一任务至多一行，幂等由 schema 保证，不由代码保证。
> **I3（一致）** 该行携带的状态 = 当次 CAS 写入的终态；投递文案由该行渲染，不重新查任务状态。
> **I4（不丢）** 进程启动时，所有 `notified_at IS NULL` 的行必须被投递恰好尝试一次；此后每轮投递周期同样。**不存在任何条件使某一行永久不被列出。**
> **I5（至少一次 / 至多一次的分界）** 标 `sent` 当且仅当一次**返回了真实成功信号**的发送之后。崩溃于「发送成功」与「标 sent」之间 ⇒ 允许重复投递一次；这是显式接受的重复，不是缺陷。
> **I6（抑制是写入期决定，不是投递期决定）** 需要抑制通知的终态写入路径（HTTP 清理），**在同一事务里就不产生可投递的行**。

I6 是你第 6 轮那条 finding 的**结构性解**：现在的做法是「先 insert pending，再 claim，再立刻 mark sent」，中间任何一刻崩溃都会留下一行会被补发的 pending——这是自找的窗口。把 `notify=False` 这个意图**下推到 `cache_manager` 的那次 INSERT**（要么不 insert，要么 `state='suppressed'` 一次写入），窗口从代码里**消失**，而不是被缩小。这条 finding 因此被**删除**，不是被修复。

### 4.2 单进程下根本不需要的机制（你问的那条，我给明确答案）

**不需要，可以整块删除：`claimed_owner`、`claimed_at`、120s 接管租约、以及围绕 NULL 的那条语义规则。**

三条独立理由：

1. **它们仲裁的并发不存在。** 单进程（事实 1/2）+ 单投递线程 ⇒ 任一时刻至多一个领取者，互斥由「线程内串行」天然提供。唯一的「另一个 owner」是**上一世进程**，而它按构造已经死了（同名容器无法并存）。
2. **即使并发发生，这套锁也救不了任何东西。** 第二个进程一启动，`app.py:381-386` 就会把第一个进程所有在途任务**无条件写成 failed**（事实 16），运行期对账的排除名单又是内存对象（事实 17）。也就是说：**在你为通知表加 owner 锁之前，多进程场景下任务状态机早已全面崩坏。** 给通知表加 fencing，等于给一艘正在解体的船的救生圈上锁。
3. **它们是三轮 finding 的唯一来源。** 第 3 轮（旧投递器清掉新租约）、第 4 轮（不同 owner 可立即抢占）、第 5 轮（`claimed_owner` 非空 + `claimed_at IS NULL` 永久卡死）——**是同一个缺陷的三次现身**：你在为 claim 定义一个跨进程的偏序关系，而 SQL 谓词表达偏序天然易错（第 5 轮的 `NULL <= x` 是 NULL，就是这个家族的经典成员）。删掉字段，这三轮 finding 连同它们未来的兄弟一起消失。

**`attempts` 上限：必须改，而且这是我发现的最严重问题（6 轮 review 无一命中）。**

`attempts < 3` 与 fail-closed 判定组合后有一个杀伤性后果。考虑两个**永久 False** 的情形，都已核实可达：

- 没有配置任何通知渠道 → `router.channels == []` → 返回 `{}` → `_notification_accepted({})` = False（空 dict 无真值）；
- 请求指定了 `channel_name="feishu"` 但只配了企微 → `_resolve_targets` 返回 `[]` → `results = {}`，且 **fallback 分支因 `targets` 为空而不触发**（事实 11）。

这两种情形下，3 次尝试后 `attempts` 达到 3 → **同一个谓词把这行从 `list_unattempted...` 里永久过滤掉** → 终态已写、用户零消息、DB 里没有任何「待处理」痕迹。**这就是 2026-09-21 事故的完全同构复现，只是换了触发条件。**

`attempts` 本身（作为计数器）保留无害；**上限必须去掉，或者改成「超限后进入显式 dead-letter 状态 + 告警日志 + 可查询」**。判据很简单：**任何让一行同时满足「未送达」且「不再被任何视图列出」的机制，都是这张卡的敌人。**

### 4.3 因此，(b+) 的最终形态

保留：CAS 同事务 INSERT（I1）、UNIQUE(task_id)（I2）、启动补发 + 周期补发（I4）、单投递线程串行、真实成败信号后标 sent（I5）、写入期抑制（I6）。
删除：`claimed_owner`、`claimed_at`、接管租约、NULL 规则、`attempts` 上限。
新增（唯一的新增）：投递点改同步发送，`sent` 才有意义。

字段从 4 降到 2（`attempts` 可选保留为观测），API 从 4 个（claim/list/mark/release）降到 2 个（list / mark_sent），共享谓词从 2 处降到 1 处，后台线程保留 1 个。**保护逻辑的规模回到被保护对象的量级以下——这正是你那条 review-discipline 判据要求的终点。**

## 五、Q3：为什么 review 不收敛

### 你的假设：成立，但它是症状不是病因

「没有写死的不变式清单，每轮重推一遍什么算对」——我核实到的**直接证据**支持它：测试类是按 finding 编号组织的（事实 20），`G1`/`H2`/`K3`/`R2`/`第 9 轮`。这些测试是**纪念碑**，不是**规格**：它们记录「上次修了什么」，不定义「什么算对」，因此无法告诉你什么时候可以停。事实 21 是这一点的代价证明——成功侧 CAS 落败被锁死了，失败侧没锁，于是 `llm_ops.py:923` 和 `transcription.py:476` 两处错误至今活着。

### 但真正的病因有三层，你只说到第三层

**病因 A：review 的终止条件是无界的。**
现行终止条件事实上是「reviewer 这一轮没找到东西」。对一个**没有规格**的代码块，一个称职的 reviewer 永远能找到东西——这不是 reviewer 失职，是任务被定义成了一个没有停机点的搜索。131 处轮次注释、单文件最高 16 轮（事实 19）说明：**这不是这个机制的偶发问题，是整个仓库的稳定态。** 你如果只给通知机制写一份不变式清单，下一个机制会重演。

**病因 B：每轮加字段，让下一轮的 finding 变得更容易，而不是更难。**
第 1 轮加 `claimed_at`，第 3 轮加 owner 锁，第 4 轮加回租约，第 5 轮补 NULL 语义。4 个字段的可表示状态组合（NULL / 非 NULL × 自己 / 他人 × 过期 / 未过期 × 计数边界）数十种，其中绝大多数在单进程下**不可达**——但它们**可表示**，所以 review 能对着它们提问，而且每个问题都是「合法」的。**保护机制在为自己的正确性制造 review 面。** 你引的那条判据（保护逻辑规模接近被保护对象即触发层级 0 审计）在这里的机械表现就是：**finding 产出速率 ∝ 状态空间大小，而状态空间由前几轮的 finding 决定。这是一个正反馈回路。**

**病因 C（你说的）：规格不在 review 输入里，于是「正确」在轮间漂移。** 第 4 轮拿旧 PR 描述判新代码，是这一层的直接后果。

还有一层你没提、但我认为对这张卡是致命的：

**病因 D：目标不可观测（§三）。** 「恰好一条、必达」在当前投递实现下无法被任何测试断言（发送返回常量 True）。**一个无法证伪的目标，会让每一轮 review 都退化成关于机制内部一致性的辩论**——这正是第 3/4/5 轮的形态：三轮都在讨论 claim 状态机自身是否自洽，没有一轮讨论用户是否收到了消息。
