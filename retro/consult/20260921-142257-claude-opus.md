- (b) 终态判定不无视产物：`_fail_non_terminal_tasks` 写 failed 前先看 `llm_status.json`。

(a) 便宜得多，且不动状态机。**我建议 (a)，并把它放进主卡**——因为它和 outbox 治的是同一次事故的同一个用户感受，分开做会让主卡的验收「收到了通知，但点进去还是一片失败」。

## 四、Q2 — 最小充分解与 outbox 的增量

### 先纠正一个前提

按你给的日志，本次终态写入发生在 **13:04:33 新进程的启动恢复**（`recover_orphaned_tasks`，`cache_manager.py:2703`），此时：进程刚起、`app.py:384` 同步调用、无 deadline 参数（`_fail_non_terminal_tasks` 的 `deadline_seconds=None` 路径，`cache_manager.py:2608-2611`）、通知渠道已由 `app.py:379 init_all_notifiers()` 初始化完毕。

**结论：一个 `finalize_terminal_and_notify()` helper 挂在 `recover_orphaned_tasks` 上，对本次事故是充分的。** 你在层次 2 里论证「补丁依赖『进程还活着』，而这类故障恰恰是进程要死」——这个论证对**关闭清算**成立，但本次触发的是**启动恢复**，进程活得好好的。

### helper 方案剩下的真实缺口有多大

| 场景 | helper 能否覆盖 | 频率判断 |
|---|---|---|
| 启动恢复写 failed（**本次**） | ✅ 能 | 每次部署都可能 |
| 运行期对账写 failed | ✅ 能 | 低频 |
| 关闭清算写 failed 后进程正常退出 | ⚠️ 状态写了、通知已提交给 wecom-notifier，但**没 flush**（层次 4）→ 大概率丢 | 需要预算没耗尽才走到，本次就没走到 |
| 关闭预算耗尽整体跳过 | ✅ 下次启动恢复兜底 → helper 覆盖 | 常见（`WORKER_STOP_TIMEOUT_SECONDS = 5.0`，`context.py:626`） |
| SIGKILL / OOM（写完终态立刻死） | ❌ 只有 outbox 能 | 低频但真实 |

**真实缺口 = SIGKILL 窗口 + 关闭清算的未 flush 窗口。第二个 outbox 也治不好。所以 outbox 独有的收益 ≈ SIGKILL 窗口。**

### 那为什么我仍然建议做 outbox？

**不是为了那个窗口，是为了 §2 的表格。** 今天的不变式散在 13 个点上、三种语义、其中两处已经跑偏（#7/#8），且这些跑偏是在 R2/K3/M1/L1/W5/G1 至少六轮 review 硬化之后仍然存在的——这本身就是「约定 + 手写」维持不住的经验证据。

outbox 相对 helper 的**增量**其实很小：helper 已经要求你把 13 个点收敛到一处；在那之后，「把通知意图和状态写进同一个 `with self._get_cursor()` 块」只是多一条 INSERT，「投递循环」只是把 router 调用从同步挪到线程。一张表 + 一个循环，换掉「5 个调用点各自守」——在本仓规模下**不算过度设计**。

**但我要求你把顺序反过来做**：先 helper 收敛 13 个点（这一步本身就修好本次事故 + #7/#8 的误发），再补 outbox 的持久化。因为如果 outbox 和收敛同卡做，一旦收敛出回归，你没法判断是新表的问题还是收敛的问题。

## 五、Q3 — 交互风险（逐条核实）

**① CAS / 终态黏性**：无冲突，而且是**助力**。`rowcount==1`（`cache_manager.py:2434`）天然给出「恰好一个胜者」，直接对应 outbox 的「恰好一行」。建议 `task_terminal_notifications.task_id` 设 UNIQUE——每任务至多一个终态，幂等由 schema 保证，不靠代码。

**② 关闭预算**：风险比你担心的小。`_get_cursor`（`:172-184`）每次调用 = 一次事务 + 一次 commit；INSERT 放进 `update_task_status` 已有的那个 `with` 块（`:2358`），**共用同一次 commit，不增加 fsync**。而且 `_fail_non_terminal_tasks` 在有 deadline 时已经逐任务收窄 busy_timeout（`:2626-2629`, `:2677-2684`），新 INSERT 自动继承这份保护。

⚠️ **但有一个你没问到的坑**：`update_task_status` 现在把 INSERT 拉进同一事务后，**outbox 写失败会连带回滚状态写**。这改变了它的失败语义。好消息是补偿通道已经存在（`terminal_write_pending`，`context.py:952/1081/1635`）；坏消息是这条通道只在 `llm_ops.process_llm_queue` 一处登记（`llm_ops.py:326`），其它 12 个点没有。这条要在卡里显式决策。

**③ InflightRegistry / terminal_write_pending**：
- `_retry_terminal_write_pending`（`context.py:1676`）直调 `update_task_status` → 若 outbox 写在其内部，**自动继承，无需改**。但它的 `error_message` 是通用文案（`:1678`），补发出去的文案会很难看，要单独处理。
- `terminal_write_pending` 是**内存 set**（`context.py:952`），进程死即丢——**不要试图把它扩展成通知 pending**，那正是 outbox 要避免的东西。
- `InflightRegistry` 与 outbox 无耦合（`context.py:638-848`），`reconcile_runtime_orphaned_tasks` 用它做排除名单，outbox 只挂在 CAS 胜者上，两者正交。

**④ 限流器权威性**：**wecom-notifier 是唯一限流权威**（`wechat.py:197-243`），outbox **绝不能**自己排队限流，否则两级队列 + 内部 65s 等待会让顺序完全不可推理。outbox 只做「取 pending → 组装 → 调 router → 标 sent」。

⚠️ **真实的乱序风险在别处**：启动补发的历史 pending 和新任务的实时通知进**同一个** wecom-notifier 队列，补发会插在前面 → 用户可能先看到昨天的失败、再看到今天的完成。**补发文案必须带原始 `completed_at` 时间戳**，否则用户会以为刚提交的任务失败了。

**⑤ 连接生命周期（你没问，但会咬人）**：连接是 thread-local（`cache_manager.py:155-165`），`close()` 只关调用线程的那条（`:2086-2089`）。投递线程会开自己的连接，`aclose()` 里的 `close()` 关不掉它。投递线程的停止与连接关闭要自己接进 `_stop_workers` 的有界等待，否则你新造一个「进程退不干净」。
