# vta-181-idle-timeout-261006 进度存档

## 里程碑 1：诊断与代码落地（commit `faaeca17`、`350a5a11`）

- 当前阶段：诊断 → 实现
- 本段结论：失败点是 SDK 的「单帧 `ws.send` 等待 > `idle_timeout`」，不是总预算超时；
  本地侧（ffmpeg 转码、base64/json、事件循环）在 17502 秒 / 410 MB 输入上实测零停顿
  >3.8 秒，可以排除本地资源打嗝。已按媒体时长显式传 `idle_timeout =
  duration/3 + 300`，拿不到时长时不传该键、逐字回退 SDK 默认 300 秒。
- 关键决策与已否决方案：
  - 已否决「加 fallback / 重试 / 防御式 try-except」：timeout 类 AsrError 不可重试是 SDK
    仓的分类，本仓不包一层。
  - 已否决「把 `idle_timeout` 做成配置项」：与 `deadline_total` 一样集中在
    `capswriter_client.py` 一处算，避免多来源漂移（#147）。
  - 已否决「直接在生产用 300 秒跑一次 17502 秒复现」：card 的实测预算只有 3 次，
    第三次必须是带修复的 E2E；复现的定量证据改用 600 秒 / 3600 秒两次梯度实测 +
    生产既有数据（12900 秒以下 10 例成功、17502 秒两例失败）来支撑。
  - 取值用「服务端读完剩余积压所需时间」这一可证上界，而不是拍脑袋的倍数。
- 下一步唯一动作：跑带修复的 17502 秒合成音频 E2E，确认转录完成并记下实测最大单帧
  等待。

## 里程碑 2：E2E 撞出服务端 14400 秒上限，改用可接受尺寸补齐 E2E（commit 见 git log）

- 当前阶段：实现 → 验收
- 本段结论：17502 秒的 E2E 没卡在发送超时上，而是拿到服务端协议错
  `code=audio_too_long`——服务端解码累计到 14400 秒就中断读取（报上来的样本数
  230412800 刚好越过 14400×16000），而生产那个文件是 17502 秒，**它在当前服务端上
  根本转不了**，卡面的 E2E 验收标准字面上无法达成。改用服务端能接受的最大尺寸
  14000 秒重跑一次，12:40:24–12:44:28 成功出文本，最大单帧等待 4.49 秒。
- 关键决策与已否决方案：
  - 已否决「拿掉 idle_timeout 改动、改写成 blocked」：即使上限问题不解决，300 秒这个
    与媒体长度无关的常数对 12900–14400 秒这类合法长音频仍然是误杀风险；改动与 4.1
    的上限问题正交，且 deadline_total 仍在总预算层面兜底。
  - 已否决「把上限问题写进代码当 workaround」：拆长音频或抬上限都是产品决策，越出本卡
    修改边界，只写进诊断文档第 6 节交主脑。
  - 实测次数从 3 次涨到 4 次，已在报告里明写：第 3 次（17502s E2E）失败后如果不补跑，
    本卡就完全没有大输入的端到端证据。
- 下一步唯一动作：跑全量测试与类型检查，提交并开 draft PR。
