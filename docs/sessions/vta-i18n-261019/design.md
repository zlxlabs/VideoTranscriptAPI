# DESIGN-note：中英双语（i18n）支持，一个全局 `language` 配置

## 目标

英文用户自托管本项目时，从部署、提交链接、查看结果页到读报错，全程不被中文卡住；
中文用户不改任何配置，行为与现在完全一致。今后加一种语言 = 加一份文案目录 + 一套生成 prompt。

## 非目标

- 按用户 / 按请求切换语言（用户已定：全局一个配置够用）。
- 企业微信 / 飞书通知的多语言（中文企业 IM，英文用户基本不会配置；且通知层用中文子串做逻辑判断，须先做状态枚举化，另立一期）。
- 日志、代码注释的英文化（不是 i18n；按项目规范逐步改，不在本批）。
- 已存历史数据的改写（旧任务失败原因、旧缓存里的「说话人N」保持原样）。
- `skill/` 目录（API 消费者侧文档）的英文化。

## 为什么不是分区 / 删除 / 约定

- **分区**：语言天然分区为「每种语言一份文案目录 + 一套生成 prompt」，各语言文件互不共享正文，中文路径一字不动，因此英文改动不会让中文质量回归。这是本方案的主干，而不是在一份 prompt 里拼接多语言指令。
- **删除**：砍掉「输出语言跟随内容语言（auto）」「界面语言与产出语言分两个键」「按请求切换」——全局单配置下它们没有消费者；砍掉缓存键改造与说话人数据迁移，改为溯源标记 + 渲染期判定。
- **约定**：内容语言（音频说什么）继续由 `language_detector` 自动判断、只决定校对 prompt，不暴露为配置；内部字典键（`"校对文本"`/`"内容总结"` 等）与校对稿「说话人：正文」的全角冒号是程序标识符，约定不翻译。

## 方案要点与已否决方案

- **要点**：
  1. **配置**：顶层 `"language": "zh-CN" | "en"`。缺省 = `zh-CN`（老部署零变更）；其他取值启动即报错（fail fast）。
  2. **i18n 核心**：包 `video_transcript_api/i18n/`，文案目录 `locales/zh-CN.json`、`locales/en.json`（扁平点分 key）；`t(key, **kwargs)` 按全局语言取文案，缺 key 直接抛错；测试锁死各语言 key 集合一致。不引入 gettext/Babel，不引入前端 i18n 运行时。
  3. **产出语言**：总结 / 笔记 / 章节的生成 prompt 按 `language` 选：中文 prompt 原样保留，英文 prompt 由英文原生撰写（不是在中文 prompt 后追加 "write in English"）。篇幅预算按语言给系数（预算按字符计，英文同信息量字符数约为中文 1.5–2 倍）。校对 prompt 仍按检测到的内容语言选择，行为不变。
  4. **缓存**：缓存键不变。在已有 `artifact_provenance` 的生成层（总结、笔记、章节、分享卡文案）写入 `language`；复用时与当前配置不一致即视为该层缺失、重新生成；旧产物无此字段按 `zh-CN` 处理。原始转录与校对层不重跑。
  5. **说话人占位名**：新产物按语言生成（`说话人N` / `Speaker N`）；渲染层判断「待确认」改为读 `speaker_inference_meta` 的 applied 标记，不再依赖中文正则；历史数据不迁移。
  6. **界面**：Jinja 模板、静态页（`index.html`/`history.html`/`app.js`）、渲染器（`dialog_renderer`/`markdown_renderer`）、分享图卡面文字、导出元数据，全部改走文案目录；`<html lang>` 跟随配置。
  7. **API 报错**：JSON 错误体增加稳定 `error_code`（snake_case，跨语言不变），`detail` 按全局语言本地化。自家前端直接显示 `detail` 无需改；第三方客户端可按 `error_code` 自行处理。任务失败原因在写入时按当时语言本地化。
  8. **文档**：新增英文 `README.en.md`，中英 README 顶部互链；`config.example.jsonc` 改为单文件中英双语注释（不拆两份示例，避免漂移），并写入 `language` 键说明。

## 篇幅预算校准（#269）

英文总结系数定为 2.4：#269 的 9 份真实样本测得，同一媒体英文与中文总结字符比中位数为 2.43。总结 hard cap 是软预算：超限时只进行一次压缩重试；若重试后仍超限，仍接受输出，不截断，也不因超限判失败。

- **已否决**：
  - `output_language: auto`（跟随内容语言）：中文用户看英文视频今天得到中文总结，这是翻译价值；auto 会让它悄悄消失。
  - `ui_locale` + `output_language` 双键：全局单配置下没有「界面英文、总结中文」的真实消费者；真出现时再加覆盖键。
  - 中文 prompt + 一句 "write in X"：与「只能使用中文书写」「标题不超过 N 字」等硬约束冲突，输出中英混杂。
  - 英文重写全部 prompt：中文输出是主力场景，已调优的中文 prompt 改写必然回归。
  - 缓存键加语言：与「改模型不重算」的既有语义不一致，且牵动整套分层复用逻辑。
  - 说话人数据迁移：历史数据渲染期判定即可，不值得改存储。
  - 错误码 + 英文消息、由客户端翻译：自家前端直接显示 `detail`，中文网页用户会看到英文报错；还要前后端各维护一份文案。
  - gettext/Babel、前端 i18n 库：规模用不上，多一套工具链。
  - README.md 直接改为英文：中文仍是主力用户，改默认入口代价大于收益；互链即可。

## 待验证前提

1. [推断] 英文总结 / 笔记 / 章节 prompt 的实际输出质量与篇幅合适——验证入口：实现卡用至少 2 份英文、2 份中文真实样本，在 `language=en` 与 `zh-CN` 下各跑一遍，对比篇幅与结构，结果写进报告。
2. [推断] 质量校验（`unified_quality_validator`）的中文评估 prompt 在英文输出下评分不失真——验证入口同上，记录英文样本的校验得分。
3. [推断] 通知层之外不存在其他「用中文子串做逻辑判断」的路径——各实现卡改动文案前先 grep 该文案是否被用作比较/匹配。

## 验收路径

1. 入口：用 `"language": "en"` 启动服务，打开首页。
2. 步骤：提交一个英文视频链接 → 历史页看到任务 → 打开结果页 → 下载 / 分享 → 用错误的 token 调一次 API。
3. 预期：页面、结果页标签、总结 / 笔记 / 章节、分享图、错误信息均为英文；同一媒体此前已有中文总结缓存时，被重新生成为英文。再用缺省配置启动，同一流程全部为中文且与改动前一致。
