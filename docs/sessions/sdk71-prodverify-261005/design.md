# SDK 492fe19 生产部署与真实验证设计

## 为什么这四条判据现在才跑得动

PR #172 已把 pin 升到 `492fe19` 并在仓内用真 websockets/真 ffmpeg 锁了三条契约，但**生产仍在跑旧 pin**：主脑部署前实测容器内 `capswriter_asr/client.py` sha256 = `eccec1a69b81c4a2360d33e15f0ddb8adffb85725dc93d41f8e3150a0863f6c7`（= `b0818dc` 那个文件），而新 pin 应为 `0490b5f877917e55f995e5ea9a81da226b47cda52e406bf361207c70550eb01b`。

这两个值的差异本身就是 C4 的「变没变」判据：部署后必须从前者变成后者。

## 仓内已证伪的前提，直接影响 C1 的解读

PR #172 的实测发现：**真被拒的 loopback 端口在旧 pin 上也是秒级 `connection_lost`**（CPython 3.11.15，5/5，0.131–0.154s）。上游 #67 的吞取消要「取消到达时等待对象恰好已完成」，真实连接失败要走 `loop.create_connection` 的两次 executor 往返，够 `deadline_watch` 重新挂上等待。

所以 C1 在生产上**预期旧形态也会绿**——它的价值是确认升级没把这条路径弄坏，**不是**证明升级修好了它。报告里必须这样写，不许把 C1 绿说成「升级修好了连接被拒」。

C2/C3 才是这次升级的实质判据（自动预算 `duration*4+120` 不再误杀长音频 + `samples_total` 对账）。

## 素材约束

- 已知生产素材：`recorder://bilibili/bilibili+30929174+1791027421/787644a07c9348b588d4b84e60336ae8` 对应 494 MB / `duration=17501.673354`（4h51m41s，纯音轨 aac 48kHz 立体声），文件在 live-recorder 宿主 `/opt/media/live_recorder/data/recordings/787644a07c9348b588d4b84e60336ae8/` 下。**本卡禁止用它做验收样本**（锁定决策 7）。
- 93.09 秒 / 306.3 秒 / 3.29× 实时是 #155 记录的唯一时长-耗时样本点；C2 的 90 秒切片要用这个量级的真实语音，好让「预算从 153s 放宽到 ~492s」这件事有可观测差异。

## 不变式

| 编号 | 不变式 | 锁定方式 |
| --- | --- | --- |
| P1 | 生产容器内 SDK 文件哈希从 `eccec1a6…` 变为 `0490b5f8…` | C4 的 sha256 实测 |
| P2 | `config.jsonc` / `users.json` / `.env` / `docker-compose.yml` 部署前后逐字节相等 | 两组 sha256 对照 |
| P3 | C1/C2 探针跑在生产容器内，证明的是镜像里那个 SDK | `docker exec` 命令原文贴报告 |
| P4 | C2 不传 `deadline_total`，走 SDK 自动预算 | 探针调用代码行贴报告 |
| P5 | C3 用 ≤15 分钟的真实直播录制，且是本次镜像首次未见的任务 | 素材 id + 首见声明 |
| P6 | C4 的否对照 UUID 命中数必须为 0，且 0 命中判据本身先被验过会变 | 两组命中数 |
| P7 | 任一副作用超时/非零后先读真实状态再决定动作 | 报告里每次副作用后的状态读数 |
