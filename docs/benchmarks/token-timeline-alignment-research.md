# Token 到时间轴对齐方案调研（#109）

## 结论

推荐用 `rapidfuzz.distance.Levenshtein.opcodes` 做 token 序列的全局编辑对齐，
保留 `TokenTimeline.start_of` / `end_of` / `quality` 的外部形状。它在本次四类
120k 字符夹具（英文、卡面原始短语重复、高重复压力、中文/中英混排）上均为
100% 正确，p50 为 20.1--50.1 ms；现有锚点链只能在部分漂移输入上正确，唯一
token 分层和分块 `difflib` 在英文/混排漂移上分别只有 0.065%/0.011% 正确，
且高重复压力耗时 6.1--6.6 s。

结论不是“锚点加一个校验”能够修复：校验最多把部分错位标 degraded，不能恢复
重复片段的身份。正确性不确定时应返回无时间（`None`/未锚定）并标记 degraded，
不能交付一个看起来完整但可能指向错误出现次数的时间。

## 复现与归因

复跑命令（在仓库根目录；依赖用 `uv --with` 临时注入，不改 `pyproject.toml`）：

```bash
uv run --with rapidfuzz --with python-Levenshtein --with edlib \
  python scripts/benchmarks/token_timeline_alignment.py --runs 5
```

复现输出（短样本使用卡面 phrase 的逻辑等价 token 流）：

```text
repro {"case": "repro_exact", "canonical_equal": true, "expected_starts": [3.0, 13.0, 23.0], "observed_starts": [3.0, 13.0, 23.0], "postcheck_flag": false}
repro {"case": "repro_drift", "canonical_equal": false, "expected_starts": [3.0, 13.0, 23.0], "observed_starts": [4.0, 14.0, 24.0], "postcheck_flag": false}
```

因此机制判断是“成立但有前提”：最终 PR #111 的规范投影完全相等时会走恒等
快速路径，卡面所写的“token 忠实反映文本”与“`_find_anchors` 错位”不能同时
发生；只要有一个前缀 token 漂移使规范串分叉，锚点链就会确定性地按扫描顺序
消耗重复子串，最小例得到 `[4, 14, 24]`。这不是随机故障，而是由重复次数、
重复子串长度、锚点大小和分叉位置共同决定的确定性故障。卡面直接给出的
`aligned_ratio=1.000/unmatched_chars=0` 在“完全相等”的最终 PR 路径上对应的是
正确恒等映射；它不能作为错位没有发生的证明。

锚点大小探针（120k 字符漂移输入）：

| 输入 | 12 | 24 | 32 |
|---|---:|---:|---:|
| 英文正确率 / p50 ms | 0.602% / 859 | 0.602% / 768 | 0.625% / 769 |
| 卡面短语重复正确率 / p50 ms | 100% / 841 | 99.975% / 820 | 99.975% / 765 |
| 高重复正确率 / p50 ms | 0.046% / 842 | 0.023% / 768 | 0.035% / 747 |
| 中英混排正确率 / p50 ms | 0.231% / 1092 | 0.222% / 1018 | 0.257% / 1136 |

增大到 24/32 只减少锚点数和索引内存，不能结构性消除错位；短文本和短句反而
更容易无锚点。高重复样本中错误率没有改善，部分更差。

## 基准环境和方法

- 机器：Intel Core i7-14700K，20 CPU；内存 48 GiB；Linux 6.8.0-142-generic。
- 运行时：`uv` 创建的 CPython 3.11.15；每个样本 5 次，报告 p50/p95。
- 样本：每类文本至少 120,031 字符；token 数 17,206--43,648。英文正常、
  卡面原始短语重复、高重复（100 个相同词组成短语）、中文/中英混排各有 clean
  与一个前缀 token drift 版本。正确率按每个文本 unit 的已知真实时间逐项比较。
- 内存是 `tracemalloc` 的 Python 峰值，不含原生扩展未被追踪的瞬时分配；依赖包
  安装体积单独列出。因此内存数字适合相对比较，不冒充容器 RSS。

候选 (a) 的后校验使用锚点密度变异系数和映射斜率变异系数：四个 drift
样本只检出高重复样本（1/4），四个 clean 样本误报 0/4。高重复样本中
`density_cv=0.000900`，但 `slope_cv=65.557234`；英文漂移虽已只有 0.602%
正确，`slope_cv=0.241790` 仍不报警。这证明“单调、有锚点、覆盖均匀”都不足以
证明身份正确。

包为 `python-Levenshtein` 0.27.5、GPL-2.0-or-later、0.469 MiB，`edlib`
1.3.9.post1、MIT、1.265 MiB。选择 RapidFuzz 是因为本次实际 opcode 测量最快且
许可证适合本仓；生产依赖落地时仍需锁版本并在 Docker 镜像中复测。

## 设计裁决

1. **结构性避免**：唯一 token 可降低错误锚定，但正常英文词汇、重复口语和中文
   字符流的唯一项都可能稀疏；只靠唯一 token 会得到大片无锚区域。全局编辑路径
   是结构性处理“插入/删除/替换”的方式；对仍存在多个等价编辑路径的区域必须
   显式标 ambiguity，不应任取一个。
2. **最诚实降级**：无法证明文本 unit 到 token 的唯一对应时返回 `None`/未锚定，
   `quality` 标记 degraded 并记录原因。时间轴是下游事实源，错误时间比缺少时间
   更难被发现，不能用 degraded 标签掩盖一个可能错误的时间。
3. **质量指标**：`unmatched_chars` 与 `aligned_ratio` 只能说明有多少字符得到
   证据，错误重复出现也能全覆盖；`coverage` 只说明尾部时间是否到达音频末端，
   单调错位时同样会全绿。三者保留作输入/产物覆盖指标，但不能作为错位守卫。
   建议新增最小结构化字段：编辑操作计数（insert/delete/replace）和
   `ambiguous_regions`/`alignment_status`；判定落在编辑路径与歧义区，而不是再
   叠加一个无语义的密度阈值。

## 迁移影响和测试处置

- `TokenTimeline.start_of`、`end_of` 的签名可以不变；`quality` 现有字段保持兼容，
  增加状态/歧义字段即可。内部 canonical 坐标仍应保持私有。
- #111 已合并的 4 组 token 风格 × 3 组内容、文本 span 守恒、单调性和生产量级
  性能夹具可复用。依赖锚点数量、`_find_anchors` 具体行为、只断言
  `unmatched_chars`/`aligned_ratio` 的测试应改为重复内容的真实时间逐项断言；
  缺 token 的降级测试保留，但增加“错误重复映射不得交付时间”的断言。
- 不建议继续在 [PR #111](https://github.com/zlxlabs/VideoTranscriptAPI/pull/111)
  上叠第五轮锚点修补。建议保留它作为历史基线，另开一个 superseding PR 落地
  RapidFuzz 方案，主脑确认新方案后再关闭旧 PR；本报告所在调研 PR 不自行合并。
